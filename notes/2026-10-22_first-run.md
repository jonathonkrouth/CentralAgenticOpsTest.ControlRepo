## How the requirements are met

- **No duplicate PRs:**
  - The worker refuses to run if the repo already has an open migration PR, a closed-unmerged one, a leftover branch, or an open review issue.
  - The PR always comes from the fixed branch `dapper-migration/ado-net-to-dapper`, and an existing branch is never recreated.
  - Only one PR per run, and failed PR creation does not fall back to opening an issue.
  - A second dispatch for the same repo waits instead of cancelling a run that's creating a PR.
- **Never merges or touches the default branch:** PRs are drafts, auto-merge stays off, and the worker can only change `.cs`, `.csproj`, and package/build props files.
- **Behavior preserved:** the worker prompt requires:
  - SQL unchanged byte-for-byte and the same parameter types;
  - the original cancellation token on every call and the same transactions;
  - first-row reads mapped to `QueryFirstOrDefaultAsync`;
  - no public API changes and no weakened tests.
- **Honest validation:** it runs `dotnet restore/build/test` before and after the change. Tests that need SQL Server are reported as "not run" with the missing prerequisite. If the migration itself breaks the build or tests, the edits are reverted and no PR is created.
- **No-op:** if no eligible ADO.NET code remains, the worker records that and creates nothing.
- **Review mode can't touch the targets:** in review mode, PR creation points at the control repo and the prompt forbids it. The output is a patch artifact plus one issue in the control repo.

## Deviations and gaps

- **No schedule:** the CAO contract normally gives new orchestrators an hourly schedule. I left it out because you asked for none.
- **No PR expiry:** gh-aw v0.92.6 only supports PR expiry within the same repository, so the cross-repo PRs don't auto-close.
- **No operational-value evaluator yet:** the outcome is measurable, but I didn't add a deterministic grader. The README records this as deferred.
- **No package-completeness tests:** this control repo has no test harness.
- **No root `aw.yml`:** the skill's root-manifest step applies to the catalog repo, not a consuming control repo.
- **Unverified until you compile:**
  - Whether `runtimes.dotnet` actually adds an SDK setup step to the compiled workflow.
  - Whether Dapper works against the target repos' fake ADO.NET test classes; the worker may need to extend those fakes.

The README also shows an optional `target-authority` entry for each target repo's `cao.json`. It's documentation only and would modify the target repos, so I left it out.

Review mode and live mode decide where a workflow's output goes. Review mode keeps everything in your control repo for you to inspect. Live mode writes the declared outputs, here a pull request, into the target repository.

### Review mode (the default)

Where output goes: all outputs go to a review repository. That defaults to the control repo (jonathonkrouth/CentralAgenticOpsTest.ControlRepo).

Targets are read-only: the target repo is only checked out and read. Nothing is pushed, opened, or commented there.
Code changes: any change that would alter target git state becomes a review bundle, an Actions artifact containing the patch and evidence. A review issue in the control repo describes it.

For dapper-migration: the worker makes the Dapper edits in its target/ checkout and runs the build and tests. It then uploads changes.patch plus validation details as an artifact, and opens one issue titled [dapper-migration:migrate] <repo> ADO.NET to Dapper migration review in the control repo.

### Live mode

Where output goes: outputs land in the target repository itself, but only through the workflow's declared safe outputs. The agent's own GitHub tools stay read-only.

For dapper-migration: the worker edits the target checkout and opens one draft pull request from dapper-migration/ado-net-to-dapper in Repo1, Repo2, or Repo3. It never merges the PR or pushes to the default branch.

## Can I use the CLI or the web app to kick off campaigns?

From Copilot:

You can do it either way, mostly. The one rule is that changing policy always means editing `cao.json` and committing it. The dashboard on GitHub Pages is a static, read-only site, so you can't launch anything from it.

| Task | CLI | github.com web UI | CAO dashboard |
| --- | --- | --- | --- |
| Start the orchestrator | `gh aw run dapper-migration …` or `gh workflow run` | **Actions → Dapper Migration → Run workflow** | No |
| Watch runs and read logs | `gh run list`, `gh run watch`, `gh run view --log` | **Actions** tab | Summarized after the next Activity run |
| Read review issues | `gh issue list/view` | **Issues** tab of the control repo | Linked or summarized |
| Download review bundles | `gh run download <run-id>` | Worker run page → **Artifacts** | No |
| Review or merge the target PRs | `gh pr view/checkout` | Target repo's **Pull requests** tab | Status only |
| Change policy (e.g. `review` → `live`) | Edit `cao.json`, then commit and push | Edit `cao.json` in the browser editor and commit | No |
| Compile workflows after editing `.md` | `gh aw compile` (CLI only) | No | No |
| Credentials and variables | `gh cao setup auth …`, `gh secret` / `gh variable` | **Settings → Secrets and variables** | No |

In practice:

- **Use the CLI for authoring.** Compiling, setup, and anything that changes workflow files needs `gh aw` and `gh cao` locally, and those changes go through Git.
- **Use whichever you prefer for operating.** Starting runs and reading results works equally well in the Actions tab; its Run workflow form shows every input with `safe_output_mode` defaulting to `review`.
- **Use the dashboard for oversight.** It shows campaign health, run history, and outcomes across your repos once Activity has collected them.

For the first run, the web UI is the easiest way to see what's happening. Click **Run workflow** on **Dapper Migration**, set `target_repo` to `jonathonkrouth/CentralAgenticOpsTest.Repo1`, and leave `safe_output_mode` as `review`. Then follow the worker run it dispatches from the Actions list.

# How to start a campaign.

Before giving you the commands, I'll check that the campaign workflows are registered and that validation is green.

Ran terminal command: gh workflow list --repo jonathonkrouth/CentralAgenticOpsTest.ControlRepo --all; "--- latest runs"; gh run list --repo jonathonkrouth/CentralAgenticOpsTest.ControlRepo --limit 6

You're ready to launch. Both Dapper workflows are registered and active, and the latest Validation, Activity, and Dashboard runs all succeeded.

You start a campaign by running its orchestrator, `Dapper Migration`. It reads `cao.json`, picks eligible targets, and dispatches one `Dapper Migration / Migrate` worker per target. You never start workers yourself, except for a manual debug preview.

## 1. First run: review mode, one repository

```powershell
cd C:\Code\cao\CentralAgenticOpsTest.ControlRepo
gh aw run dapper-migration --ref main `
  --raw-field target_repo="jonathonkrouth/CentralAgenticOpsTest.Repo1" `
  --raw-field max_repos="1" `
  --raw-field rollout_percent="100" `
  --raw-field safe_output_mode="review"
```

You can also use plain `gh` with the same inputs:

```powershell
gh workflow run "Dapper Migration" --repo jonathonkrouth/CentralAgenticOpsTest.ControlRepo `
  -f target_repo=jonathonkrouth/CentralAgenticOpsTest.Repo1 -f max_repos=1 -f rollout_percent=100 -f safe_output_mode=review
```

Or use the web UI: **Actions → Dapper Migration → Run workflow**, then fill in the same fields.

## 2. Watch it

```powershell
gh run list --repo jonathonkrouth/CentralAgenticOpsTest.ControlRepo --limit 5
gh run watch --repo jonathonkrouth/CentralAgenticOpsTest.ControlRepo
```

The orchestrator finishes in a few minutes with an **Orchestrator Report** in its run summary. It then dispatches `Dapper Migration / Migrate · …Repo1 · review`, which takes longer because it runs the .NET build and tests twice.

## 3. What a successful review run looks like

- **Review issue:** a new issue appears in the control repo titled `[dapper-migration:migrate] jonathonkrouth/CentralAgenticOpsTest.Repo1 ADO.NET to Dapper migration review`. It includes the summary, the preservation checklist, validation results, and an agent prompt.
- **Review bundle:** the worker run has an artifact named `review-jonathonkrouth-CentralAgenticOpsTest.Repo1-…` containing `changes.patch`, `validation.txt`, and related files. Download it with:

  ```powershell
  gh run download <worker-run-id> --repo jonathonkrouth/CentralAgenticOpsTest.ControlRepo
  ```

- **Repo1 is unchanged:** no branch, PR, or issue appears there.
- **A `noop` is also a valid outcome**, for example `existing migration PR` or `no eligible ADO.NET query code remains`.

Activity collects these runs on its next hourly pass, and they then appear on the dashboard.

## 4. Widen, then go live

1. **Review all three:** leave out `target_repo` and set `max_repos="3"`.
2. **Go live:** change one target's `"mode"` from `"review"` to `"live"` in `cao.json`, then commit and push. Rerun step 1 for that repository with `safe_output_mode="live"`. This creates a draft PR from `dapper-migration/ado-net-to-dapper` in that repo.
3. **Repeat** for the other two repositories.

If you request `live` before changing the policy, the run is rejected at admission instead of quietly falling back to review. That rejection confirms the guardrail works.
